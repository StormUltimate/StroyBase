# StroyBase: Архитектура страницы корпуса и пошаговый план

**Цель:** Унифицировать UI корпуса с этажом, добавить роли, вкладки ПД/РД/ИД/Договора/Графики, breadcrumb в стиле проводника, исправить 400 при редактировании, (бонус) редактирование фото и привязка к меткам.

---

## 1. ТЕОРИЯ: Архитектура и UX

### 1.1 Иерархия и контекст

- **Проект → Корпус → Этаж** остаётся неизменной.
- Страница **корпуса** — контекст «все этажи корпуса»: медиа и документы могут быть общими по корпусу или привязаны к этажу.
- Страница **этажа** — контекст одного этажа: медиа, документы, материалы, планы.

### 1.2 Единый шаблон объекта (Building + Floor)

**Предложение (Grok):** Один общий шаблон `app/templates/shared/object_view.html`, от которого наследуют страницы корпуса и этажа.

**Архитектура:**

- **Базовый шаблон** `shared/object_view.html`:
  - Двойная боковая панель (левая контекстная + глобальная из base).
  - Блоки: «Назад», карточка объекта (название, класс/тип, кнопки Редактировать/Удалить), кнопка «Загрузить фото/документы».
  - Для корпуса: список этажей + «Добавить этаж»; для этажа — детали этажа (площадь, заметка).
  - Область контента: опциональный баннер (только для корпуса), панель фильтров, табы, `{% block tab_content %}`.

- **Переменные контекста** (передаёт route):
  - `view_type`: `'building'` | `'floor'`
  - `entity`: экземпляр Building или Floor
  - `floors`: список этажей (для корпуса)
  - `back_url`, `back_label`
  - `edit_url`, `delete_url`, `upload_url`
  - Для этажа: `building`, `materials`, `plans` и т.д.

- **Наследники:**
  - `buildings/view.html` → `extends "shared/object_view.html"`, переопределяет блоки табов и контента под корпус (в т.ч. «Выбрать этаж», баннер ролей, вкладка «Договора»).
  - `floors/view.html` → тот же базовый шаблон, блоки под этаж (материалы, планы, без списка этажей).

Итог: один скелет, два варианта контента; дублирование минимизировано, единый стиль фильтров и табов.

### 1.3 Баннер ролей на странице корпуса

**Роли:** Заказчик, Технадзор, Генподрядчик, Застройщик, ООО и т.д.

**Варианты хранения:**

| Вариант | Плюсы | Минусы |
|--------|--------|--------|
| **JSONField `participants` в Building** | Один столбец, гибкая структура | Сложнее запросы/фильтрацию по ролям, тип JSON в PostgreSQL |
| **Модель BuildingParticipant** | Нормализованные данные, удобно расширять (даты, контакты) | Отдельная таблица, миграции вручную в pgAdmin |

**Рекомендация:** Модель **BuildingParticipant** (id, building_id, role_name, company_name, contact_info — все поля кроме id nullable=True). В будущем можно добавить даты, подпись и т.д. Роли выводим баннером под заголовком корпуса.

### 1.4 Документы: ПД / РД / ИД / Договора

**Предложение (Grok):** Один blueprint `documents` с мощной фильтрацией.

**Реализация:**

- **DocType** уже есть (виды работ/категории). Можно ввести «категорию документа»: ПД, РД, ИД, Договор — через отдельное поле в DocType или отдельную таблицу `document_category` (id, name, code: 'pd'|'rd'|'id'|'contract').
- **Фильтрация:** по project_id, building_id, floor_id (опционально), категория (ПД/РД/ИД/Договор), вид работ (DocType), даты, поиск по названию.
- **Вкладки на странице корпуса:** «ПД», «РД», «ИД», «Договора» — одна и та же разметка (таблица/сетка документов), различаются только предустановленным фильтром категории.
- **Общий шаблон вкладки документов:** например `shared/documents_tab.html` с параметрами `documents`, `filter_category`, `show_floor_column` и т.д.

Итог: один механизм документов, разные вкладки = разные фильтры.

### 1.5 Вкладка «Графики» (ГПР и ГДРС)

- Отдельная вкладка «Графики» на странице корпуса.
- Выбор даты (date picker) → по этой дате показывается список работ (из справочника или из связи с документами/задачами).
- Клик по виду работы → переход к документам, отфильтрованным по этой дате и типу работы (открытие в той же вкладке или модалке).

Данные: либо отдельная сущность «График работ» (дата, тип работы, ссылка на документ), либо теги/категории у документов с датой. Для первого этапа достаточно фильтра по дате + по виду работ в существующих документах.

### 1.6 Breadcrumb в стиле проводника Windows

- Компонент `app/templates/shared/breadcrumb.html`: путь вида «Все объекты > Проект X > Корпус Y > Этаж Z».
- По клику на сегмент — выпадающий список соседних элементов того же уровня (например, клик по «Корпус Y» — список всех корпусов проекта; по «Этаж Z» — все этажи корпуса).
- Небольшой JS: показ/скрытие dropdown по клику, навигация по выбранному элементу.

Использование: на главной (список объектов), на dashboard проекта, на странице корпуса, на странице этажа.

### 1.7 Исправление 400 при редактировании корпуса

- POST `/buildings/edit/<id>` возвращает 400: типичные причины — отсутствие/невалидный CSRF, неверный Content-Type или пустое тело.
- В коде уже есть `csrf_token` в форме; нужно проверить: что форма действительно отправляет token, что маршрут принимает POST, и что в модели/БД нет лишних полей (например `uploaded_by_id` в Document — если колонки нет в модели, убрать передачу или добавить колонку вручную в БД и в модель).

## 4. РЕКОМЕНДАЦИИ И АЛЬТЕРНАТИВЫ

1. **Порядок 1 → 2 → 3:** Сначала 400, потом визуальная унификация без рефакторинга, затем вынос в object_view — так меньше риска сломать текущую верстку за один шаг.
2. **BuildingParticipant vs JSONField:** Рекомендуется отдельная модель для участников — проще расширять и соблюдать политику nullable в БД.
3. **Documents blueprint:** Имеет смысл вводить после шага 7: сначала общий шаблон вкладок документов в текущих blueprints, затем при росте логики вынести в отдельный blueprint `documents` с общей фильтрацией.
4. **Breadcrumb:** Можно сделать сначала статический путь без dropdown (просто ссылки), затем добавить выпадающие списки — разбить на два подшага при нехватке времени.

## 5. ПЕРВЫЙ ШАГ К ВЫПОЛНЕНИЮ

### Задача для выполнения: Шаг 1 — Исправить 400 при редактировании корпуса

**Цель:** После нажатия «Сохранить» на странице редактирования корпуса форма должна успешно отправляться (редирект на просмотр корпуса), без ответа 400 Bad Request.

**Причины 400 (типичные):**
- Невалидный или отсутствующий CSRF-токен (Flask-WTF возвращает 400 при ошибке CSRF).
- Форма не попадает в запрос (например, не тот action или method).

**Что сделать:**

1. **Проверить форму в `app/templates/buildings/edit.html`:**
   - Убедиться, что `<form method="POST" action="{{ url_for('buildings.edit_building', building_id=building.id) }}">` и что внутри есть `<input type="hidden" name="csrf_token" value="{{ csrf_token() }}"/>`.
   - Если токен уже есть — проверить, что форма не дублируется и что при рендере страницы редактирования в контексте есть `building` (чтобы `building.id` был определён).

2. **В `app/blueprints/buildings/routes.py` в `edit_building`:**
   - При ошибке валидации (пустое имя) не делать редирект без сообщения; вернуть `render_template('buildings/edit.html', building=building)` с `flash`, чтобы пользователь видел ошибку.
   - Убедиться, что при GET возвращается шаблон с `building` в контексте (уже так).

3. **Убрать возможную причину 500 при загрузке документов (чтобы не путать с 400):**  
   В `upload_building_documents` при создании `Document(...)` не передавать `uploaded_by_id`, если в модели `Document` нет такого поля (иначе при загрузке файла на странице корпуса будет 500). Если поле есть в БД — добавить его в модель с `nullable=True`.

**Файлы для изменения:**
- `app/templates/buildings/edit.html` — при необходимости поправить форму/CSRF.
- `app/blueprints/buildings/routes.py` — логика ответа при ошибке валидации; убрать или согласовать `uploaded_by_id` при создании Document.
- `app/models.py` — только если решено добавить `uploaded_by_id` в Document (nullable=True).

**Критерий успеха:** Открыть страницу редактирования корпуса, изменить название и нажать «Сохранить» → ответ 302, редирект на `/buildings/<id>`, без 400.
