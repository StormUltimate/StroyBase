## 4. Устранение артефактов (реализовано)

1. **Корпуса и этажи не отдаются в HTML**: в select только «Не привязан»; списки подгружаются по API **только** после выбора проекта (корпуса) и корпуса (этажи). Иерархия жёсткая: проект → корпуса этого проекта → этажи выбранного корпуса.
2. **API**: `api_buildings` и `api_floors` требуют соответственно `project_id` и `building_id`; при отсутствии параметра возвращают 400. Возвращают только отфильтрованные записи с санитизированными названиями.
3. **Проекты**: в контекст отдаётся `projects_display` с санитизированными именами вместо сырых `projects`.
4. **Кодировка в БД**: при сохранении битых данных в `buildings.name` / `floors.name` в списках они не попадают в модалку в сыром виде; при необходимости исправить значения в pgAdmin.

## 5. Санитизация названий и защита от дубликатов

### Backend (routes.py)

- **`_sanitize_display_name(s, fallback)`**  
  - Удаляются управляющие символы (`\x00`–`\x1F`), кроме `\t`, `\n`, `\r`.  
  - Допускаются только фрагменты, совпадающие с regex `[а-яА-ЯёЁa-zA-Z0-9\s\-.,()\/№]+` (кириллица, латиница, цифры, пробелы, `-.,()/№`). Всё остальное (в т.ч. `@`, иероглифы, битые байты) удаляется.  
  - Подряд идущие пробелы схлопываются в один.  
  - Если результат короче 2 символов, или состоит только из цифр и пунктуации, или не содержит ни одной буквы — возвращается `fallback`. Так отсекаются артефакты вида «Jb @ air6 10» и прочий мусор.

- **`_dedupe_by_id(items, id_key, fallback_name_template)`**  
  В ответах API дубликаты по `id` отбрасываются, у записей с пустым `name` подставляется имя по шаблону. В выпадающих списках каждый id встречается один раз.

- **API**  
  `api_buildings` и `api_floors`: выборка только по своей области (`project_id` / `building_id`), санитизация, дедупликация по id, **сортировка по названию** (по алфавиту). При использовании fallback для названия в лог пишется `logger.debug` (подозрительное имя).

### Frontend (index.html, JS)

- При добавлении опций используется **Set** по `id` — дубликаты по id не попадают в DOM.
- Текст опции задаётся через **`textContent`** (защита от XSS).
- При открытии модалки без выбранного проекта списки «Корпус» и «Этаж» очищаются.

### Очистка данных в БД (однократный скрипт)

См. раздел **7. Data cleanup (скрипт)** ниже.

## 6. UX: иерархия, загрузка при открытии, спиннер

- **Иерархия**  
  «Корпус» доступен только при выбранном проекте; «Этаж» — только при выбранном корпусе. При смене проекта список корпусов перезапрашивается, список этажей очищается.

- **Загрузка при открытии модалки**  
  При открытии модального окна проверяется выбранный проект (из preset или из значения select). Если проект выбран — сразу запрашиваются корпуса (`loadBuildings`). Если передан preset корпуса/этажа — после загрузки корпусов подставляется корпус и запрашиваются этажи, затем подставляется этаж.

- **Спиннер**  
  Во время запроса к API у полей «Корпус» и «Этаж» отображается спиннер (Bootstrap `spinner-border`), скрывается по завершении запроса.

- **Без проекта**  
  Если при открытии модалки проект не выбран, поля «Корпус» и «Этаж» остаются неактивными (disabled), списки не запрашиваются.

## 7. Data cleanup: скрипт санитизации и дедупликации названий (buildings / floors)

Однократная очистка уже сохранённых в БД данных. Проект не использует Alembic; скрипт выполняется вручную.

### Назначение

- **Санитизация** всех полей `name` в таблицах `buildings` и `floors`: допустимы только кириллица, латиница, цифры, пробелы, символы `-.,()/№`; удаляются управляющие символы и мусор; пустые/невалидные заменяются на «Корпус {id}» / «Этаж {id}».
- **Дедупликация**: в пределах одного проекта для зданий — уникальность по `(project_id, нормализованное_имя)`; в пределах одного корпуса для этажей — по `(building_id, нормализованное_имя)`. При конфликте остаётся запись с минимальным `id` (старейшая); ссылки с дубликатов переназначаются на неё, затем дубликаты удаляются.

### Логика

- Функция `normalize_name()` и ключ для дедупликации вынесены в **`app/utils/sanitize_names.py`** (та же логика, что и в API `_sanitize_display_name`).
- **Скрипт:** `scripts/sanitize_building_floor_names.py`. Последовательно: (1) обновление названий в `buildings` батчами; (2) обновление названий в `floors`; (3) поиск дубликатов зданий, переназначение FK (floors, documents, material_movements, schedule_works, building_participants), удаление дубликатов; (4) то же для этажей (переназначение FK во всех таблицах, ссылающихся на `floors`), удаление дубликатов.
- Лог пишется в **stdout** и в файл вида **`logs/sanitize_YYYYMMDD_HHMMSS.log`** (каталог создаётся при необходимости). Откат (downgrade) не предусмотрен — скрипт меняет только данные.

### Аргументы CLI (argparse)

| Аргумент | Описание |
|----------|----------|
| `--dry-run` | Только симуляция: вывести, что было бы изменено/удалено, без COMMIT и без записи в БД. |
| `--batch-size N` | Размер батча для коммитов (по умолчанию 100). |
| `--yes`, `-y` | Пропустить запрос подтверждения при удалении более 10% записей. |
| `--restore-prefixes` | Восстанавливать известные сломанные префиксы (по умолчанию вкл). |
| `--no-restore-prefixes` | Не восстанавливать «Корпус N»/«Этаж N» из сломанных строк. |
| `--quiet`, `-q` | Не выводить каждую замену before→after, только сводки и предупреждения. |

### Запуск

Из корня проекта (реальное выполнение):

```bash
python scripts/sanitize_building_floor_names.py
```

Сначала проверить без изменений в БД (рекомендуется):

```bash
python scripts/sanitize_building_floor_names.py --dry-run
```

С указанием размера батча и без интерактивного подтверждения:

```bash
python scripts/sanitize_building_floor_names.py --batch-size 50 --yes
```

Через Flask shell (без аргументов CLI — по умолчанию без dry-run, batch_size=100):

```bash
flask shell
>>> from scripts.sanitize_building_floor_names import run
>>> from app import create_app
>>> run(create_app(), dry_run=False, batch_size=100, skip_confirm=False)
```

### Известные сломанные шаблоны названий и восстановление

После санитизации по regex часть символов «Корпус»/«Этаж» может отображаться как мусор (неверная кодировка). Скрипт при включённом `--restore-prefixes` (по умолчанию) распознаёт такие строки и подменяет их на «Корпус N» / «Этаж N» (число берётся из строки или из `id` записи).

| Исход (в БД или после санитизации) | Восстановление |
|------------------------------------|----------------|
| `а гб 6`, `а г б 7` (кириллица а, г, б — остатки «Корпус») | «Корпус 6», «Корпус 7» |
| `jb @ air 6`, `korpus 3`, `корпус 2` | «Корпус 6», «Корпус 3», «Корпус 2» |
| `т аж 1`, `аж 2`, `etazh 3` (остатки «Этаж») | «Этаж 1», «Этаж 2», «Этаж 3» |

Логика реализована в **`app/utils/sanitize_names.py`** (`restore_known_patterns()`). Используется простое сопоставление по regex, без ML. Если шаблон не совпал, остаётся результат обычной санитизации или fallback «Корпус {id}» / «Этаж {id}».

### Предупреждение и подтверждение

- **Необратимость:** скрипт выполняет UPDATE и DELETE; откат не предусмотрен. Перед первым запуском рекомендуется сделать снимок БД (pg_dump или резервная копия).
- **Защита от массового удаления:** если число записей, которые будут удалены как дубликаты (buildings + floors), превышает 10% от общего числа записей (buildings + floors), скрипт запрашивает подтверждение: введите `yes` для продолжения или `no` для отмены. Флаг `--yes` отключает запрос (удобно для скриптов и CI).

## 8. Ручная очистка лишних корпусов через админ-интерфейс

Автоматическое массовое удаление корпусов по скрипту рискованно из‑за возможных внешних ключей и разной семантики «лишних» записей. Поэтому в интерфейсе отображаются **все** корпуса, а удаление выполняется вручную с явным выбором действия.

### Маршруты (admin)

| Маршрут | Метод | Описание |
|---------|--------|----------|
| `/admin/buildings` | GET | Список всех корпусов: проект, название, кол-во этажей, кол-во записей движения материалов, дата создания, примечание. Сортировка по проекту и названию. Доступ: только роль `admin`. |
| `/admin/buildings/<id>/delete` | POST | Удалить корпус полностью: обнуляются привязки документов, движений и работ в графике к корпусу; этажи и сам корпус удаляются. |
| `/admin/buildings/<id>/reassign` | POST | Переназначить все связи (этажи, документы, движения, график, участники) на другой корпус того же проекта (параметр `target_building_id`), затем удалить текущий корпус. |

### Поведение в UI

- На странице «Корпуса» — таблица Bootstrap с колонками: Проект, Название, Этажей, Движений материалов, Дата создания, Примечание, Действия (кнопка «Удалить»).
- Поиск по таблице (клиентский фильтр по проекту, названию, примечанию).
- При нажатии «Удалить» открывается модальное окно с предупреждением о последствиях и двумя вариантами:
  - **Удалить полностью** — каскадное удаление (этажи и данные по корпусу удаляются, привязки к корпусу обнуляются).
  - **Переназначить на другой корпус** — выбор корпуса того же проекта из выпадающего списка; все связи переназначаются на выбранный корпус, затем текущий корпус удаляется.
- Если у проекта больше 10 корпусов, выводится баннер: «Обнаружено много корпусов — проверьте на дубликаты».

Защита: все маршруты под декоратором `@admin_required` (проверка `current_user.role == 'admin'`).

## 9. Поведение при удалении и предотвращение «сирот»

### Текущее поведение (модели и БД)

- **Project:** в SQLAlchemy у проекта заданы связи `buildings` и `documents` с `cascade='all, delete-orphan'`. При удалении проекта через `db.session.delete(project)` удаляются связанные корпуса и документы. У корпуса заданы `floors`, `participants` и (через backref) `schedule_works` с каскадом. Связь с **MaterialMovement** у проекта без каскада, поэтому перед удалением проекта в коде явно удаляются записи движения и связи MovementDocument.
- **Building:** при удалении корпуса через приложение (админка) сначала обнуляются привязки в Document, MaterialMovement, ScheduleWork, затем удаляются этажи и сам корпус. В БД у части таблиц заданы `ON DELETE CASCADE` / `SET NULL` в комментариях (реализуется вручную в pgAdmin при создании таблиц).
- **Сироты:** если проект был удалён напрямую в БД (например, без `ON DELETE CASCADE` на `buildings.project_id`), в таблице `buildings` остаются строки с `project_id`, которого нет в `projects` — это корпуса-сироты. Они попадают в выпадающие списки и в отчёты.

### Удаление проекта в интерфейсе

- Маршрут `GET/POST /project/<id>/delete`: при **GET** показывается страница подтверждения с итогом «Будет удалено: X корпусов, Y этажей, Z документов, N записей движения, …». При **POST** с параметром `confirm=yes` выполняется каскадное удаление: сначала удаляются связи и записи движения по проекту, затем вызывается `db.session.delete(project)` (удаляются корпуса, этажи, документы и прочие связанные сущности по связям SQLAlchemy), затем удаляется каталог медиафайлов проекта. Без явного подтверждения удаление не выполняется.

### Очистка корпусов-сирот

- Скрипт **`scripts/clean_orphan_buildings.py`** находит корпуса, у которых `project_id` отсутствует в таблице `projects`.
- Запуск: `python scripts/clean_orphan_buildings.py --dry-run` — только вывод списка; `--delete` — удалить сироты (каскад по этажам и связям); `--reassign-to-project ID` — переназначить всех сирот на указанный проект.
- Рекомендуется сначала выполнить `--dry-run`, при необходимости сделать снимок БД, затем выполнить `--delete` или `--reassign-to-project`.

### Рекомендации

- Не удалять проекты/корпуса напрямую в БД без учёта каскада; использовать интерфейс удаления проекта или админку корпусов.
- Периодически проверять сирот: `SELECT * FROM buildings b WHERE NOT EXISTS (SELECT 1 FROM projects p WHERE p.id = b.project_id);` и при необходимости запускать скрипт очистки.
